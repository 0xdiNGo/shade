# Threat model

This document enumerates the security properties Shade actually provides at v0.1, the assumptions those properties depend on, and the failure modes operators should plan for. It is *not* a marketing page — every claim that doesn't hold today is flagged.

## Trust boundaries

| Boundary | What's inside |
|---|---|
| **One Shade node** | The daemon process, its SQLite store, its TLS material, its mesh PSK. |
| **The botnet (mesh)** | All Shade nodes that share the botnet CA + mesh PSK. |
| **The IRC server (single network)** | The IRCD itself; its services, if any. |
| **The operator workstation** | Whatever holds the admin client cert / shadectl invocations. |

The IRC server is **not trusted for op authority**. It is trusted to deliver messages and to authenticate other clients via SASL.

## Adversaries we plan against

| Adversary | What they can do | What stops them today |
|---|---|---|
| Network-side eavesdropper | Read or modify mesh traffic. | mTLS over rustls; HMAC-SHA256 cookie verification on op MODEs. |
| Compromised IRC user | Spoof a hostmask, send PRIVMSGs. | Hostmask matching is identification-only; permissions live in `channel_user_flags`. |
| Compromised single Shade node | Issue arbitrary IRC commands, broadcast bogus mesh frames. | Role rotation: a node only acts on roles it holds. Other nodes flag uncertified ops within the 5 s grace window; ≥ 5 uncertified ops in 10 s trips automatic deop of every recently-opped victim by the deterministic ROLE_OP holder, with a 60 s cooldown to prevent flapping. The mesh PSK + CA are still leaked, so the next step is rotation (see `docs/Operations.md`). |
| Compromised peer cert | Connect to the mesh, exchange `PeerHello`, push upserts. | Cert SAN is bound to `node_id`; `PeerHello.node_id` must match. CA pinning prevents an unrelated CA's certs from authenticating. Stolen-cert revocation is a CRL-list TODO (v0.2). |
| Compromised mesh PSK | Mint valid cookies for any channel. | Full rebuild required — operator runbook covers PSK rotation. |
| Network partition | Both halves think they hold `ROLE_OP`; double-ops happen. | Cookie verification keeps both ops legitimate (only the mesh sees who issued each). On heal, snapshot reconciliation makes the eligible-peer set whole again before the next rebalance tick. |
| Hijacked admin client cert | Hit `/v1`, write arbitrary state. | Native mTLS verification on the admin listener: `WebPkiClientVerifier` rooted at `admin.client_ca`, cert Subject CN bound to `User.handle`, every request audited under that handle. Lost certs still require operator-driven CA rotation until CRL/OCSP lands (v0.2). |

## What we don't defend against

* **The IRC server going hostile.** Services-issued bans we'd treat as authoritative; a fully malicious IRCD can lie about everything. Out of scope.
* **Admin client compromise.** Whoever holds the admin certificate is the operator, period. Token revocation is a v0.2 item.
* **Side-channel attacks on the bot host.** RAM forensics, kernel exploits, etc. We're not a hardened enclave; we're a daemon that runs as `nonroot` in a distroless container.
* **Resource exhaustion via legitimate-looking IRC traffic.** Mode-flood detection is best-effort warning; full DoS resistance requires upstream controls.

## Property summaries

* **Confidentiality of mesh traffic** — mTLS (rustls, modern ciphers, client + server cert verification). At v0.1 the trust root is a self-signed CA generated by `shade init-ca`; rotation is operator-driven.
* **Authenticity of cross-bot ops** — HMAC-SHA256 cookies over typed payloads, HKDF-SHA256 per-channel keys, ULID `request_id` + ring-buffer dedupe + 60-second window. Wraith's MD5+counter scheme is replaced; see [Improvements Over Wraith § 4](Improvements-Over-Wraith.md#4-md5-cookie--per-bot-counter-for-op-replay-prevention).
* **Authenticity of replicated state** — last-write-wins on `(updated_at, origin_node)`. A peer with a valid cert can lie about state, but only its own writes get accepted (other nodes' rows have other `origin_node` values); rolling back a peer's state requires that peer's cooperation or a manual edit.
* **Audit integrity** — per-node `audit_log` table, intentionally not mesh-replicated. Each node records what *it* did. Cross-node history is reconstructed by pulling each node's audit log separately. A compromised node can rewrite its own audit log; it cannot rewrite a peer's.

## Failure modes operators should plan for

1. **Mesh PSK leak.** Procedure in `docs/Operations.md`: pause writes, rotate PSK, redeploy, force snapshot resync. Cookie ops re-derive keys automatically.
2. **CA private-key leak.** Re-bootstrap the CA on a new node, reissue every node cert, re-deploy. Procedure in `docs/Operations.md`.
3. **Single node compromise without immediate detection.** Time window between compromise and detection is bounded by the mass-op trip threshold (5 uncertified ops in 10 s) and operator vigilance on the audit log. The automatic deop reverses observable damage; logging into the box and inspecting the SQLite + audit_log state is the recovery path.
4. **Network partition longer than the cookie grace window.** Cookies time out; the partition halves cannot certify each other's ops. Reconnect resumes normal operation; ops issued during the partition are recorded but not certified post-fact (the relevant grace window has passed).

## Open security work

| Item | Why it's open | Tracked in |
|---|---|---|
| Cert revocation list / OCSP | Lost admin or node certs still require CA rotation. | v0.2 |
| Per-handle login rate limit | `/v1/login` doesn't yet rate-limit Argon2id verifies — a determined attacker can grind the password space at one Argon2 verify per request. Mitigated by the password requirement itself (Argon2id m=64MiB t=3) and by mTLS being the default auth path; tighten when the API is exposed beyond a trusted operator network. | v0.2 |
| Formal external review | We've reviewed our own code; that is not the same thing. | When the project graduates beyond pre-alpha. |
